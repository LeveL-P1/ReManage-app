## 1. What this project is

**ReManageSociety** (package name `society-app`, product name **ReManage Society**, Android app id `com.society.management`) is a **multi-tenant SaaS platform for housing-society / apartment-complex management in India**.

One deployment serves many societies. Each society is a tenant with its own residents, flats, committee, finances, staff, gate operations, and community life. The platform covers the full operational surface of a residential society:

- **Money** — maintenance billing, invoices, double-entry ledger, payments, receipts, expenses, funds, budgets, payroll, bank reconciliation, auditor exports.
- **Gate & operations** — visitor lifecycle, guard console, parcels, domestic staff, attendance, parking, vendors, assets, SOS, blacklist, patrols.
- **Community & governance** — notices, helpdesk/complaints, documents, meetings, polls, events, forum, marketplace, resident directory.
- **Society administration** — member/tenant records, occupancy, move-in/out, imports, NOC issuance, access control, audit trail, settings.
- **Platform layer** — a separate owner/partner portal that provisions, disables, and soft-deletes societies.

The product is explicitly India-oriented: ₹ formatting, `en-IN` dates, UPI-style payment fields, GST on bills, owner/tenant separation, domestic-help management, police-verification documents for tenant move-in, society NOC certificates, WhatsApp messaging, and English/Hindi/Marathi UI.

Delivery surfaces:

| Surface | How it is delivered |
|---|---|
| Web app (desktop + mobile web) | Next.js 16 App Router |
| Guard console | Standalone public route `/gate`, PIN login, PWA-friendly |
| Android app | Capacitor 6 shell wrapping the deployed web app |
| Dedicated mobile API | NestJS `api/mobile/v1/*` with its own OTP/device-session auth and an OpenAPI-generated TypeScript SDK |
| Platform portal | `/registered-society` with a separate `portal_session` cookie |

### 5.2 Layered code architecture

The NestJS side follows a strict, repeated four-file pattern per domain:

```
<domain>.controller.ts   HTTP shape, DTO validation, permission action declaration
<domain>.service.ts      business rules, audit events, orchestration
<domain>.repository.ts   Prisma access, tenant filtering
<domain>.<*>.test.ts     colocated unit tests for each of the above
```

Pure domain rules live one level further out, in framework-free workspace packages (`@society/finance-core`, `@society/operations-core`, `@society/society-core`, `@society/community-core`, `@society/security`, `@society/ux-core`). These packages have no Nest, no Next, and no Prisma imports — they take plain snapshots in and return decisions out (e.g. `evaluateNocEligibility`, `evaluateDuesEnforcement`, `assertCanSubmitMoveWizard`, `evaluatePermission`, `buildNavigationModel`). That is what makes the 202 unit tests cheap to run.

The Next.js BFF (`src/app/api/**`) is the older layer: route handlers call `getSession()`, then Prisma directly, with domain helpers pulled in from `src/domain/` and `src/lib/*-service.ts`. It is being progressively shimmed to Nest — see §22.

### 5.3 The three request paths

| Path | Auth | Consumer | Status |
|---|---|---|---|
| `src/app/api/**` (BFF) | web session JWT (cookie or Bearer) | Next.js screens, guard console, public pages | Primary today |
| `api/v1/**` (Nest) | BFF bridge JWT or OIDC principal | BFF shims, future clients | Built out, flag-gated (`NEST_SHIM_ENABLED`) |
| `api/mobile/v1/**` (Nest) | mobile access token + device session | native/Expo mobile client via `@society/sdk` | Contract published (47 paths) |

`src/lib/api/route-disposition.ts` records the intended fate of every BFF prefix: `keep-bff`, `shim-to-nest`, `deprecate-410`, or `remove`. Shimmed routes emit `Sunset`, `Link: rel="successor-version"`, and `X-Legacy-Api-Route` headers (`buildDeprecationHeaders`).

## 6. Identity, sessions & authentication

The repository contains **four independent authentication systems**. This is intentional — each has a different threat model and client.

### 6.1 Web session (residents, committee, treasurer, platform admin)

- Email + password. `bcrypt.compare` against `User.password`.
- Rate limited per IP (`authRateLimit`).
- On success `createSession()` resolves the user's **first active `SocietyMembership`** and mints an HS256 JWT (`jose`, 7-day expiry) containing:
  `userId, membershipId, societyId, role (productRole), permissionRole, name, email, flatId, mfaVerified?, expiresAt`.
- A `UserSession` row records IP, city, country, OS, browser (non-fatal on failure) — this powers the device/session list.
- **Token transport is unusual and deliberate:** `createSession(user, { persistCookie: false })` — the login API returns `sessionToken` in the JSON body. The client stores it in `localStorage` under `rms.session` (`src/lib/client-session.ts`) and sends `Authorization: Bearer <token>` on every request. `localStorage` (not `sessionStorage`) is used specifically so the Capacitor Android WebView keeps the session across app restarts; a legacy `sessionStorage` key `rms.tabSession` is migrated forward on read.
- The cookie path still exists for the HTML form flow: `POST /api/auth/login` with `redirect=1` 303s to `/auth/complete?token=…&next=…`, which hands the token to the tab.
- `getSession()` prefers the `Authorization: Bearer` header, then falls back to the `session` cookie.

**Login refusal cases** (`src/app/api/auth/login/route.ts`):

| Condition | Result |
|---|---|
| Bad email/password | `401 invalid_credentials` |
| Inactive user *with* a pending membership | `403 membership_pending` (drives the pending-approval modal) |
| No active membership at all | `403 membership_pending` |
| Society `deletedAt` or `accessDisabledAt` set | `401 invalid_credentials` (deliberately indistinguishable) |
| Society `subscriptionEnd` in the past | JSON `{ expired: true }` / redirect to `/expired` |

### 6.2 Guard session

- Phone + 4-digit PIN against `GuardUser.pin` (bcrypt), optionally scoped by `societyId` since one phone can exist in several societies.
- `GuardUser.isActive = false` → "Guard access is pending committee approval".
- Guards self-request access with a society join code (`POST /api/guard/join`); a committee member approves.
- Guards operate the standalone `/gate` console, which is on the public-path allowlist and does not use the dashboard shell.

### 6.3 Portal session (platform owner / partner)

- Separate `PortalAdmin` table (`role: owner | partner`), separate `portal_session` cookie, separate secret (`PORTAL_SESSION_SECRET`, falling back to `SESSION_SECRET`/`AUTH_SECRET`/`NEXTAUTH_SECRET`).
- Serves `/registered-society` and `/api/portal/**`. `/api/portal` is on the public-path allowlist precisely because it authenticates itself.

### 6.4 Mobile session (NestJS `api/mobile/v1`)

The most hardened of the four:

- Two entry points: `POST /auth/password` and `POST /auth/otp/request` → `POST /auth/otp/verify`.
- OTP challenges are stored hashed (`MobileOtpChallenge`: `identifierHash`, `codeHash`, `attempts`, `expiresAt`, `consumedAt`) and delivered over SMTP.
- Password login is rate limited on **three** independent axes: identifier hash, installation id, and network address. A `DUMMY_PASSWORD_HASH` is compared on unknown users to equalize timing.
- Success issues a short-lived access token plus a rotating refresh token bound to a `MobileDeviceSession` row: `installationId`, `platform`, `appVersion`, `activeRole`, `activePermissionRole`, `refreshFamilyId`, `refreshTokenHash`, `refreshRotation`, `version`, `expiresAt`, `revokedAt`.
- `MobileSessionGuard` re-validates **every** claim against the live DB row on each request — session id, user, society, membership, active role, active permission role, and `version` must all match, the role/permission-role pair must be legal (`isPermissionRoleValidForMobileRole`), and the role must still appear in the membership's approved `SocietyRoleAssignment` rows. Any mismatch → 401. This makes server-side revocation instantaneous.
- Mobile roles are a narrowed set: `resident` and `guard` only (`mobileRoleForProductRole`). `PUT /session/active-role` switches between them for dual-role users.

### 6.5 Keycloak / OIDC (present, dormant)

`infra/keycloak/society-connect-realm.json` plus `apps/api/src/security/{jwt-principal-verifier,composite-jwt-principal-verifier,bff-bridge-jwt-verifier}.service.ts` implement an OIDC path. `KEYCLOAK_ENABLED` defaults to `false`; the composite verifier lets the Nest API accept either a Keycloak token or a BFF bridge token.

## 7. Authorization model

Authorization is expressed in **three layers that map onto each other**.

### 7.1 Layer 1 — product roles (what users see)

`chairman`, `secretary`, `treasurer`, `member`, `tenant`, `guard`, `watchman`, `vendor_staff`, `facility_manager`

### 7.2 Layer 2 — permission roles (what the policy engine evaluates)

`society_admin`, `committee`, `treasurer`, `member`, `tenant`, `resident`, `guard`, `platform_admin`

Mapping (from `re-auth-sys.md` and `mapProductRoleToPermissionRole`):

| Product role | Permission role | Scope |
|---|---|---|
| Chairman | `society_admin` | Full control of their own society only |
| Secretary | `committee` | Operations, residents, occupancy, notices, helpdesk |
| Treasurer | `treasurer` | Finance and audit only |
| Guard / Watchman | `guard` | Gate, visitors, security operations |
| Flat owner | `member` | Own flat + resident features |
| Tenant | `tenant` | Own flat + tenant features |

### 7.3 Layer 3 — permission actions (26 verbs)

Defined in `packages/security/src/permission-policy.ts` and mirrored in `packages/ux-core/src/index.ts`:

```
audit:event.read
society:onboard | core.manage | settings.manage | directory.read
society:finance.manage | finance.read | occupancy.manage | import.manage
operations:gate.manage | visitor.respond | read | manage | booking.manage | sos.raise
community:read | notice.manage | helpdesk.respond | helpdesk.manage | document.manage
community:governance.manage | vote.cast | rsvp.manage | post | moderate
tenant:membership.read
```

`evaluatePermission({ principal, action, societyId })`:

1. `resolveTenantContext` finds the principal's membership for the requested society. No membership → `platform_admin` override, else `TenantAccessError`.
2. Finds any active role holding the action; none → deny with `No active role can perform <action>`.
3. If the action is in `MFA_REQUIRED_ACTIONS` and `mfaVerified` is false → deny.

`MFA_REQUIRED_ACTIONS` = `audit:event.read`, `society:onboard`, `society:finance.manage`, `operations:manage`, `community:document.manage`, `community:governance.manage`.

### 7.4 Enforcement points

| Point | Mechanism |
|---|---|
| `src/proxy.ts` | Public-path allowlist → session decode → `canAccess(permissionRole, pathname, ctx)` on **API routes only**; also per-user rate limit and security headers |
| HTML pages | Client-side `TabSessionGate` + `GuardRedirect` (pages are *not* blocked server-side by the proxy — the API behind them is) |
| BFF handlers | `requirePermission(module)` / `requireAdmin()` in `src/lib/rbac.ts` |
| Nest controllers | `AuthenticationGuard` + declared permission action per endpoint |
| Mobile controllers | `MobileSessionGuard` + role/permission-role pair validation |
| Navigation | `buildNavigationModel(persona, allowedActions)` — hides items the actions don't allow |
| Database | Optional PostgreSQL RLS (§8) |

`packages/security/src/legacy-route-policy.ts` bridges old URL prefixes to actions — e.g. `/api/expenses` → `society:finance.manage`, `/api/activity-log` → `audit:event.read`, `/api/my-visitors` → `operations:visitor.respond`, with a universal prefix list (`/dashboard`, `/api/auth`, `/api/search`, `/profile`, `/my-society`, `/services`, …) that every authenticated role may reach.

## 8. Multi-tenancy & data isolation

Isolation is defence-in-depth with four layers:

1. **Session-bound tenant.** Every session carries exactly one `societyId`, derived server-side from `SocietyMembership`. The browser never proposes a society. Multi-society membership per user is explicitly out of scope for v1.
2. **Query filtering.** Nearly every Prisma call filters on `societyId`; almost every model carries the column and is indexed on it.
3. **Tenant context resolution.** `resolveTenantContext` rejects any request whose principal has no membership in the requested society (`TenantAccessError`), except for `platform_admin`, which is recorded as `source: "platform-admin-override"`.
4. **PostgreSQL Row-Level Security.** `packages/db/src/rls-policy.ts` generates, per table:

   ```sql
   ALTER TABLE "x" ENABLE ROW LEVEL SECURITY;
   ALTER TABLE "x" FORCE ROW LEVEL SECURITY;
   CREATE POLICY tenant_isolation ON "x"
     USING       ("societyId" = current_setting('app.current_society_id', true))
     WITH CHECK  ("societyId" = current_setting('app.current_society_id', true));
   ```

   `withTenantSession(pool, societyId, fn)` sets `app.current_society_id` as a transaction-local setting around the work and clears it after. Gated by `TENANT_RLS_ENABLED`, applied with `npm run db:rls:apply`, and covered by `tenant-rls-manifest.ts` plus `tests/integration/cross-tenant.api.test.ts`. Identifiers are validated against `^[A-Za-z_][A-Za-z0-9_]*$` before interpolation.

**Society lifecycle flags** on the `Society` model gate access independently of auth: `deletedAt` / `deletedByPortalAdminId` / `deletionReason` (soft delete), `accessDisabledAt` / `accessDisabledByPortalAdminId` / `accessDisableReason` (suspension), and `subscriptionEnd` (expiry → `/expired`).

## 9. Data model (89 Prisma models)

PostgreSQL, `prisma-client-js`, cuid primary keys, no native enums (status columns are strings with the legal values documented in comments). Grouped by domain:

### Tenant & people (7)
`Society`, `Flat`, `Unit`, `Person`, `UnitOccupancy`, `User`, `Tenant`

- `Society` holds the tenant config: `joinCode`, `totalFlats`, `maintenanceAmt`, `dueDayOfMonth`, `lateFee`, `upiId`, `bankDetails`, `planTier`, `openingBalance`, `logoUrl`, `slaConfig` (JSON per complaint category), `subscriptionEnd`, `rechargeHistory`, `emergencyPhone`, `legalAdviserName/Phone`, `duesEnforcementEnabled/Days`, `moveInShiftingCharge`, `moveOutShiftingCharge`, `meterRatesJson`, plus the lifecycle flags above.
- **`Flat` is the legacy shape; `Unit` + `Person` + `UnitOccupancy` is the modern shape.** Both coexist. `src/domain/unit-migration.ts` (`ensureUnitForFlat`) bridges them, and `UnitOccupancy` carries `relationshipType` (`OWNER` / `TENANT` / …) and billing responsibility.

### 12.2 The nav catalog

`NAV_CATALOG` is a single declarative array of 36 entries. Each entry declares `href`, `label`, `iconKey`, `sectionTitle`, `sectionOrder`, the `personas` it belongs to, and the `requiredActions` (OR-semantics). Sections in order: *(unsectioned home)*, `OPERATIONS`, `FINANCE`, `COMMUNITY`, `GOVERNANCE`, `MANAGEMENT`, `PLATFORM`.

`buildNavigationModel(persona, allowedActions)` filters by persona **and** permission, groups by section, sorts pinned-first then alphabetically, and drops empty sections. `filterNavItems` does the flat variant. This one catalog drives the sidebar, the bottom nav, and the command palette — so a permission change reshapes the whole UI consistently.

## 14. Core workflows end-to-end

### 14.1 Society bootstrap (chairman self-service)

```
/register → name, email, password, phone, society name, address
  ↓  atomic transaction
  User(email, passwordHash, active)
  Society(name, address, server-generated joinCode)
  SocietyMembership(productRole=chairman, permissionRole=society_admin, status=active)
  ↓
session issued → /dashboard
  ↓
Settings → flats/wings setup, billing config, SLA, meter rates
Credentials → create Secretary / Treasurer / Guard for THIS society only
Share joinCode with residents
```

Server-side invariants: the browser never proposes a role; a chairman can only create staff for their own `societyId`; one email → one society in v1.

### 14.2 Resident onboarding

```
/join
  joinCode → normalizeJoinCode → resolve society
  pick existing flat/unit (or request a new one)
  declare relationshipType: OWNER | TENANT  → role member | tenant
  optional: moveInDate, agreementEndDate, emergencyContact, isPrimaryOccupant, vehicleCount
  ↓
User created (isActive may be false)
SocietyMembership(status = "pending")
ensureUnitForFlat() bridges legacy Flat → Unit
billing responsibility defaults: OWNER → OWNER, TENANT → TENANT
  ↓
Login attempt while pending → 403 membership_pending → pending-approval modal
  ↓
Committee: /members or memberships queue
  POST /api/memberships/[id]/approve  → status=active, activatedAt, membership.flatId set
  POST /api/memberships/[id]/reject   → status=rejected, rejectedAt
  ↓
Resident logs in → resident persona → /dashboard
```

### 14.3 Guard onboarding & the gate loop

```
POST /api/guard/join  (society join code)  → GuardUser(isActive=false)
Committee approves                          → isActive=true

  ↓ /gate console (public route, no dashboard shell)
```

### 14.5 Billing → ledger → payment → receipt

This is the most carefully written path in the repo (`src/domain/maintenance-finance.ts`):

```
MaintenanceBill (amount + gstAmount + lateFee = totalAmount)
  │
  ├─ ensureMaintenanceBillInvoice()
  │     invoiceNumber = INV-<JOINCODE>-<PERIOD>-<FLAT>-<id6>
  │     creates Invoice + InvoiceLineItem
  │     posts:  DR 1100 Accounts receivable   CR 3000/3010 Income
  │
  └─ recordMaintenanceBillPayment()
        guards: amount > 0, ≤ invoice total, never below already-paid
                ("Recorded payments are immutable")
        delta = desiredPaid − previouslyPaid
        if delta > 0:
          Payment(status=SUCCESS, method)
          Receipt(receiptNumber = generateSocietyReceiptNumber(joinCode, year, seq))
          posts: DR 1000 cash | 1010 bank    CR 1100 Accounts receivable
          Invoice.paidAmount += delta ; status → PARTIAL | PAID
        Bill.status → pending | partial | paid
```

Idempotency: `postLedgerEntries` short-circuits if a `FinancialTransaction` already exists for `(societyId, sourceType, sourceId)`. Balance: `assertBalancedLedger(lines)` throws on any debit≠credit set. Missing accounts are auto-created from `DEFAULT_LEDGER_ACCOUNTS` before posting, and a missing code after that is a hard error.

### 14.6 Public payment link

```
Committee: POST /api/maintenance/bills/[id]/payment-link → BillPaymentLink(token)
Share link (WhatsApp / SMS)
Resident opens /pay/<token>   ← public path, no login
  GET  /api/pay/[token]        → bill summary
  POST /api/pay/[token]/confirm → records payment through the same ledger path
```

### 14.7 Dues enforcement

## 19. Security posture

### Headers
Set twice — statically in `next.config.ts` and again per-response in `src/proxy.ts` (`withSecurityHeaders`):
`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`, `Strict-Transport-Security: max-age=31536000; includeSubDomains`, and a CSP that tightens in production (drops `unsafe-eval`, `ws:`, and the jsdelivr font source). Nest applies its own `SecurityHeadersMiddleware` + `RequestIdMiddleware` on `*`.

> Note: the two `Permissions-Policy` values differ — `next.config.ts` sends `camera=(), microphone=(), geolocation=()` while `proxy.ts` sends `camera=(self), microphone=(self), geolocation=(self)`. The proxy value is the one that reaches proxied responses, and it is the one the guard console needs for camera capture.

### Secrets
Both `src/lib/session.ts` and `src/lib/portal-auth.ts` resolve their signing key lazily via a local `getSessionSecret()`, and both **throw at runtime in production** when the secret is missing or shorter than 32 characters. Lazy evaluation keeps builds from crashing. `packages/config/src/production.ts` (`assertProductionReady`) runs at Nest API and worker boot.

### Rate limiting
- `authRateLimit(ip)` on login.
- `apiRateLimit(userId)` on every authenticated API request in the proxy, **fail-open** if Valkey is down (explicitly commented as a local-dev accommodation).
- Mobile password login: three-axis limiting (identifier / installation / network) over a 15-minute window.
- `packages/security/src/{rate-limit-core,rate-limit-server,valkey-rate-limit}.ts` + `apps/api/src/security/valkey-rate-limit-store.ts`.

### Audit
`ActivityLog` and `SecurityEvent` models; `apps/api/src/security/audit-log.service.ts` and `packages/security/src/audit-event.ts` (`createAuditEvent`). Mobile auth wraps its audit sink so a delivery failure warns rather than breaking login.

### Files
`file-storage-policy.service.ts` + `s3-presigned-url.service.ts` — private buckets, signed URLs, no public object access.

### Other
- Password hashes never logged; login errors are deliberately uniform between "no such user", "wrong password", "society deleted", and "society disabled".
- `npm run audit:gate` (`scripts/npm-audit-gate.mjs`) with a checked-in baseline (`docs/security/audit-baseline.json`) and `tests/security/npm-audit-baseline.test.ts`.
- `npm run prod:check` / `prod:check:strict` (`scripts/production-readiness-check.mjs`).
- SQL identifier allowlisting in the RLS generator.
- `tests/integration/cross-tenant.api.test.ts` and `tests/integration/mfa-privileged.test.ts` guard the two highest-severity risks.

## 22. Migration state & known tensions

This repo is mid-migration on several axes at once. Reading it without knowing that is confusing, so:

### 1. Next BFF → NestJS
Two full API implementations coexist. The web UI still calls `src/app/api/**`; the Nest `api/v1/**` layer is complete for society-core, finance-core, operations, and community, but is only reachable through `NEST_SHIM_ENABLED` + the BFF bridge JWT. `src/lib/api/route-disposition.ts` is the authoritative map of what is `keep-bff` (auth, sessions, search, dashboard, push, mobile, guard login/join) versus `shim-to-nest` versus `remove` (`/api/legal-adviser`, already superseded by non-advisory document templates).

### 2. `Flat` → `Unit` + `Person` + `UnitOccupancy`
The modern occupancy model exists and is used by newer code (parking sharing, occupancy commits, join flow), but `Flat` and `User.flatId` are still load-bearing across most screens. `src/domain/unit-migration.ts` bridges them on write.

### 3. MFA: removed but still enforced in policy
`re-auth-sys.md` puts MFA explicitly out of scope for v1, and migration `20260623002000_remove_mfa_totp_columns` dropped the TOTP columns. Yet `MFA_REQUIRED_ACTIONS` still gates six privileged actions on `mfaVerified`, `SessionPayload.mfaVerified` remains optional (so effectively `false`), and `tests/integration/mfa-privileged.test.ts` asserts the behaviour. Recent commits (`fix(security): restore privileged MFA enforcement`) show this being actively contested. **Treat `mfaVerified` as the live switch for privileged actions and check how it is populated before changing anything here.**

### 4. Two permission systems, one policy engine
`src/lib/role-access.ts` (route prefixes) and `src/lib/rbac.ts` (module permissions) were flagged in the roadmap as duplicate models. They have since been rewired to both delegate to `@society/security` — but they still present two different APIs, and `canAccessWithoutSession` keeps a hardcoded `CLIENT_NAV_PREFIXES` fallback used whenever society/subject context is missing.

### 5. Pages are not server-gated
`src/proxy.ts` enforces RBAC on `/api/*` only. HTML page protection is client-side (`TabSessionGate`, `GuardRedirect`). This is a deliberate consequence of the Bearer-token-in-`localStorage` session model — the proxy cannot see the token on a plain navigation. The data behind each page is protected; the shell is not.

### 6. Workers are structural, not yet durable
Queue job builders, dedupe ids, retry counts, and idempotency tests are all in place; BullMQ/Valkey connection is still a logged placeholder.

### 7. Keycloak/OIDC is wired but off
Realm, verifiers, and composite principal resolution exist; `KEYCLOAK_ENABLED=false`.

### 8. Roadmap phase state
`docs/PRODUCT_PRODUCTION_ROADMAP.md` tracks Phases 0–8; its progress log records **Phases 5, 6, 7, and 8 complete (CP1–CP8)**. Its "Current App Snapshot" section is now stale (it cites 78 models / 88 API routes / 48 pages; the repo is at 89 / 121 / 59) — treat that section as historical and this document as current.

### 9. Repo hygiene
`.next/`, `node_modules/`, `test-results/`, and `tsconfig.tsbuildinfo` (483 KB) are present in the working tree. `.env` exists alongside `.env.example`. `src/app/dashboard-wrap-fixture/` and `src/app/modal-fixture/` are empty directories. `README.md` duplicates its final two sections. A `pnpm-workspace.yaml` sits next to npm workspaces + `package-lock.json` — npm is the real package manager.

## 23. Conventions & glossary

### Conventions
- **Imports** — `@/` → `src/`; `@society/<pkg>` → `packages/<pkg>/src/index.ts` (aliased in `tsconfig.json` and `vitest.config.ts`). Nest files import workspace packages by **relative path with `.ts` extension** (`../../../../../packages/security/src/index.ts`) because they run under tsx/NodeNext.
- **Money** — `Float` in Prisma, `roundMoney(x) = Math.round(x*100)/100` everywhere, `toLocaleString("en-IN")` for display.
- **Status columns** — plain strings with the legal union in a trailing comment. No Prisma enums anywhere.
- **Nest v1 verbs** — every `api/v1/**` endpoint is `POST`, including reads (`.../list`, `.../read`).
- **Tests** — colocated `*.test.ts` beside the unit under test; cross-cutting suites under `tests/`.
- **Domain purity** — anything in `packages/*-core` must stay free of Nest, Next, and Prisma.
- **Errors** — Nest returns RFC 7807 problem+json (`ProblemJsonFilter`, `MobileProblemFilter`); the BFF returns `{ error, code? }` JSON.
